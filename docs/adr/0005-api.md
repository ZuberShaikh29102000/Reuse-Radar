# ADR 0005 — Public API: read-only DRF, search without model calls, free-tier deployment

Status: accepted · Date: 2026-10-02

## Endpoints

All are `GET`, JSON, anonymous, and paginated where they return lists (25 per page, ≤ 100).
Schema: `/api/schema`. Docs: `/api/docs`.

| Path | Purpose |
|---|---|
| `/api/gaps` | The triage queue. Open gaps (missing, uncertain, no_record), most severe first, then by confidence. Filters: `status`, `product_type` (comma lists), `year`, `severity`, `min_severity`. |
| `/api/papers` | Papers. Filters: `year`, `processing_status`, `has_hepdata`. Ordering: `readiness`, `-readiness`, `date`, `-date`. |
| `/api/papers/{inspire_id}/gaps` | One paper with every current product and its HEPData status. |
| `/api/stats` | Corpus totals: processing status, products by type, gaps by status and severity. |
| `/api/search?q=` | Full-text search over product descriptions, paper titles and evidence. |
| `/api/products/{id}/similar` | Products closest in meaning, using stored embeddings (pgvector). |
| `/healthz` | Liveness and database check for Render. |

Every response carries the links a curator needs: INSPIRE, arXiv, the HEPData record, and the DOI
of the matched table. It also carries the match scores, so a decision can be checked.

Invalid filters return **400** with the allowed values, instead of being ignored. An unknown
product type silently returning nothing would look like "no gaps".

## No model in the request path (SPEC section 2, item 2)

The SPEC asks for "pgvector-backed search" and "no model calls anywhere in the request path".
Embedding a user's free-text query would itself be a model call, so search is split in two:

- **Text search** uses Postgres full-text search (`websearch_to_tsquery`, ranked with weights:
  description > title > evidence). It needs no model. A smoke test caught a real bug here.
  `ts_rank` gives non-matching rows a tiny positive rank, so filtering on `rank > 0` returned every
  product. The query now filters on the match itself (`tsvector @@ tsquery`), and a regression
  test covers it.
- **Similarity search** ("more like this product") compares embeddings the offline pipeline
  already stored, using cosine distance on the HNSW index.

A test imports the URL configuration in a fresh interpreter and fails if any of these were
imported: the LLM router or cache, any pipeline module, `fastembed`, `onnxruntime`, or `httpx`.
The web build also does not install the ML libraries: `fastembed` is in an optional `pipeline`
extra.

*Rejected:* embedding queries at request time with the local MiniLM model. It breaks the SPEC
rule, and needs about 100 MB of model in a free 512 MB instance.

*Rejected for now:* a stored `tsvector` column with a GIN index. At the expected size (about 7K
products) on-the-fly vectors are fast enough. Add the column if `EXPLAIN` shows otherwise.

## Read-only, anonymous, protected

- No authentication backends, sessions, cookies or admin. `django.contrib.auth` is not even
  installed, so there is nothing to attack in that sense. Writes return 405.
- Anonymous throttling at 120 requests/min per client (`API_RATE_LIMIT`) protects the free
  instance and database.
- CORS allows only the origins configured in `CORS_ALLOWED_ORIGINS` (the Phase 6 frontend), and
  only `GET`.
- HTTPS redirect behind Render's proxy, and `nosniff` headers.

**Update (Phase 6):** the one write endpoint, `POST /api/reviews` (accept or reject a declared
product), needs a curator token.

- Tokens come from `REVIEWER_TOKENS` (`name:token,…`, at least 24 characters each; weaker values
  fail loudly at request time) and are compared in constant time.
- The reviewer name is taken from the token, never from the request body.
- Reviews have their own throttle (60/min per curator), and CORS allows `POST` for this endpoint.
- Review history is public: `GET /api/products/{id}/reviews`, and each product carries its
  `latest_review`.

*Rejected:* Django users and sessions. The curator group is tiny, there is no login UI, and
installing `django.contrib.auth` and sessions would add attack surface to a mostly read-only
service.

## Deployment

- **Render free web service** (`render.yaml`): `uv sync --locked --no-dev`, migrations at start-up
  (safe with one instance), gunicorn with 2 workers, health check `/healthz`.
- **Supabase or Neon Postgres** with pgvector, through the connection pooler with
  `sslmode=require`.

Secrets are entered in the dashboard (`sync: false`), and `DJANGO_SECRET_KEY` is generated by
Render. `docs/deploy.md` has the step-by-step checklist.

**Verify at deploy time** (could not be tested from here):
- the exact Supabase pooler hostname and port for the project
- whether Render's free instance reaches the database host (direct Supabase hosts may be
  IPv6-only)
- Render's current free-tier sleep behaviour
